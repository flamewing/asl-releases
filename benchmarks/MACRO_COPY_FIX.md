# Global macro-copy initialization (2026-10-06)

Pristine Windows GCC builds of unchanged `930b9b0` intermittently fail `t_maclines` with a spurious macro-recursion error. The global-copy branch allocates a `MacroRec` but initializes neither `UseCounter` nor `LstMacroExpMod`, `LocIntLabel` and `GlobalSymbols`. These fields subsequently control recursion, listing, internal-label substitution and symbol scope. A standalone check of the actual copy block, with allocation filled with nonzero bytes, reproduces incorrect state with Windows GCC, Windows MSVC and Linux GCC.

Initialize the copy from the original definition, reset its invocation counter to zero, then replace all owned pointers with the existing deep copies. This preserves definition options while keeping invocation state and storage independent. The poisoned-allocation check now passes with all three compilers. Extend `t_maclines` with repeated calls to a globally copied definition using internal labels, global symbol visibility and suppressed listing expansion, with independently specified expected bytes. All 210 CTest cases pass for each toolchain.

This is a correctness correction, not an optimization result. It provides a concrete explanation for intermittent macro-depth symptoms previously encountered in fresh experimental builds; it does not retrospectively establish the outcome of those discarded performance trials. Rebase the listing/string experiments on this correction before timing them. No production timings were collected for the initial failing trial builds.
