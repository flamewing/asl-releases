Separate migration advisories: -Wunsafe-buffer-usage
==================================================

The baseline records 19,231 distinct file/line/flag entries for this category. A fresh local scan emits 21,368 observations across 210 translation units, including repeated header diagnostics. These are different counting populations; the numbers are not a warning-regression comparison.

Clang describes this diagnostic as identifying raw indexing, pointer arithmetic and certain C buffer functions for migration to bounds-safe C++ containers/views. Merely checking a C index against a length does not remove the diagnostic. Clang explicitly describes applying this programming model to plain C as unergonomic and points to the separate, developing -fbounds-safety approach.

Source: https://clang.llvm.org/docs/SafeBuffers.html, sections Pre-Requisites and Buffer operations should never be performed over raw pointers, inspected 2026-10-28.

The user explicitly selected "Classify migration advisories separately" on 2026-10-28. Accordingly, this category is separated from the completed control-flow and concrete memory-warning work. Its existence does not establish an out-of-bounds access; its syntactic nature also does not prove the underlying accesses safe. No warning flags or pragmas were disabled. A comprehensive bounds-proof audit or adoption of another buffer-access model would be separate work, rather than an outstanding requirement of this triage. The five individually proved cases below remain useful supporting evidence; their proofs are not generalized to other sites.

Individually reviewed bounded operations
=======================================

The view primitives below require that a nonempty borrowed view identifies len live bytes; this is their documented API precondition. NULL is permitted only with length zero. The proofs establish the primitive's accesses under that precondition, not that every caller supplies a valid view. Their existing tests use nonterminated arrays, sentinel bytes just outside the view, empty NULL views and oversized offsets/counts. Removing these diagnostics would require hiding the C pointer operations or adopting a different container/access model; neither would improve the present code's legibility.

strref.h:20, as_strref_sub: offset is clamped to len before advancing the pointer. A zero offset avoids arithmetic on NULL. Nonzero offsets are at most the live range length, permitting at most its one-past address. The remaining length is reduced by that same offset, and count only shortens it.

strref.h:28, as_strref_trim_left: each iteration requires len != 0 before reading the current byte; after reading it, the pointer advances by one and len decreases by one. Thus neither the next dereference nor the increment can pass the represented range.

strref.h:35, as_strref_trim_right: len != 0 guards len-1, which is necessarily an index in the live range. Each iteration reduces len and does not advance the base pointer.

strcomp_view.h:46 and 52, as_strref_find_quoted: the loop requires i < text.len before accessing text.data[i] or returning text.data+i. Empty views execute no iteration, including NULL empty views. Quote/escape/nesting state affects delimiter selection, not the iteration bounds. Existing exhaustive short-input tests compare the delimiter result against the legacy scanner while placing delimiter/quote sentinels immediately beyond the counted slice.
